# Collaborative Sheet

브라우저 탭 여러 개에서 같은 시트를 함께 편집하는 웹 스프레드시트다. AI에게 범위 편집을 맡길 수도 있는데, AI가 낸 값은 원래 값과 비교해 본 뒤에 적용한다.

- 구현 범위: 엑셀처럼 쓰는 편집(선택, 입력, 키보드 이동, 서식 단축키, 복사/붙여넣기, 실행 취소, 새로고침 뒤에도 유지), 탭 간 공동 편집(참여자 이름과 색, 접속자 목록, 다른 사람의 선택과 입력 중 표시, 내 변경만 실행 취소), AI 편집(셀 단위 스트리밍, 중지, 미리보기, 적용/버리기, 한 번에 되돌리기), 공동 편집과 AI가 부딪히는 상황의 정책, 우클릭 메뉴.
- 구조: pnpm workspace로 나눴다. 도메인 로직은 `packages/sheet-core`, Next.js 앱은 `apps/web`에 있다. 자세한 배치는 `docs/architecture/folder-structure.md`, 진행 기록은 `docs/spec/gap-analysis.md`에 있다.

**읽는 순서**
- 문서: 이 README를 먼저 읽는다. 결정의 자세한 근거와 검토한 대안은 `DESIGN.md`에 있고, README 표에 절 번호를 적어 두었다. LLM을 어떻게 썼는지는 `LLM_REPORT.md`에 있다. 나머지 루트 문서(`AGENTS.md`, `CLAUDE.md`, `TECH_RULES.md`)와 `docs/`, `.codex/`는 AI Agent가 작업할 때 읽는 규칙 문서다.
- 코드: `packages/sheet-core/src/sheet.ts`(셀 스키마, 연산, 실행 취소 범위)에서 시작해 `apps/web/src/collab/broadcastProvider.ts`(탭 간 동기화), `apps/web/src/hooks/useSheet.ts`와 `useSheetCommands.ts`(편집), `apps/web/src/hooks/useAiEdit.ts`와 `apps/web/src/app/api/ai/route.ts`(AI 흐름), `packages/sheet-core/src/ai/proposal.ts`(제안 판정과 충돌) 순서로 보면 된다. core 모듈 옆의 `*.test.ts`가 곧 동작 명세다.

## 배포

https://collab-sheet-gamma.vercel.app (Vercel, 실제 AI 연결). 가입이나 로그인 없이 바로 쓸 수 있다.

- 공동 편집: 같은 브라우저에서 이 주소를 탭 여러 개로 연다. 헤더의 [새 탭에서 함께 편집]을 눌러도 된다. 탭마다 이름을 정하면 각자 다른 참여자가 된다. 다른 브라우저나 기기와는 연결되지 않는다(명세 범위).
- AI 편집: 범위를 고르고 툴바의 AI 편집 버튼(⌘K / Ctrl+K)을 누르거나, 우클릭해서 "AI로 편집…"을 고른다. 제안은 시트 위에 원래 값과 함께 보이고, [적용]을 눌러야 시트가 바뀐다.
- 가짜 응답으로 바꾸는 버튼은 주소에 `?debug=1`을 붙였을 때만 보인다.

**체험 순서**
1. 이름을 정하고 몇 칸에 숫자를 입력한다. ⌘B(굵게)와 ⌘Z(실행 취소)도 눌러 본다.
2. 헤더의 [새 탭에서 함께 편집]으로 탭을 하나 더 열고, 두 창을 나란히 둔다. 한쪽에서 입력하거나 선택하면 다른 쪽에 바로 보인다.
3. 숫자가 든 범위를 고르고 ⌘K를 눌러 지시를 보낸다. 빈 패널의 예시를 눌러도 된다. 셀이 하나씩 채워지고, 도중에 [중지]할 수 있다. 칸 위에는 원래 값과 제안 값이 같이 보인다.
4. 검토하는 동안 다른 탭에서 그 범위의 한 칸을 고쳐 본다. 그 칸에 "지금 … · 건너뜀"이 뜨고, [바뀐 1칸 빼고 적용]을 누르면 나머지 칸만 바뀐다. ⌘Z 한 번이면 AI 적용 전체가 되돌아간다.

## 공동 편집과 AI가 만나는 지점: 결정과 이유

세 상황 모두 원칙 하나로 정했다. **사람에게 알리고, 사람의 최신 편집을 지킨다.** AI는 보조 도구다. AI가 결과를 만드는 사이에 사람이 직접 바꾼 값이 더 최신의 판단이다. 자세한 근거와 검토한 대안은 `DESIGN.md` 13절과 15절에 있다.

**AI가 결과를 만드는 동안 다른 참여자가 대상 셀을 수정하거나 삭제하면?**
결과를 버리지 않는다. 바뀐 칸만 "원래 값이 바뀜"으로 표시한다. 빨간 테두리를 두르고 칸 위에 "지금 9999 · 건너뜀"처럼 지금 값을 보여 준다. 적용 버튼은 [바뀐 n칸 빼고 적용]으로 바뀌고, 누르면 그 칸은 건너뛰고 나머지만 반영한다.

여기서 "원래 값"은 요청을 보낸 순간의 값이다. AI는 그 값을 보고 계산했다. 요청 뒤에 바뀐 칸에 AI 값을 덮어쓰면 다른 사람의 편집을 지우거나, 낡은 값으로 계산한 결과가 들어간다. 모든 칸이 바뀌었으면 적용 버튼을 잠그고 다시 요청하게 한다.
- 고르지 않은 안: 확인을 받고 덮어쓰기(남의 최신 편집을 지울 수 있다), 결과 전체 무효화(한 칸 때문에 전부를 잃는다).

**한 사람이 AI 결과를 검토하는 동안 다른 참여자에게는 무엇이 보여야 하나?**
누가 어느 범위를 AI로 만들고 있는지, 또는 검토하고 있는지만 보인다. 요청한 사람의 색으로 그린 점선 범위, "서연 · AI 검토 중" 같은 이름표, 참여자 목록의 상태가 그것이다. 제안 값은 보여 주지 않는다. 적용할지 정해지지 않은 값이 다른 사람 화면에 뜨면 확정된 값으로 오해할 수 있어서다.

제안은 요청한 사람 탭의 초안이다. 새로고침해도 남고, 탭을 닫으면 사라진다. 시트에는 적용된 값만 들어간다. 다른 참여자는 그 범위를 계속 편집할 수 있고, 그 편집은 위의 규칙으로 보호된다.

**두 사람이 겹치는 범위에 동시에 AI 편집을 요청하면?**
막지 않고 알린다. 보내기 전에 내 대상이 다른 사람의 AI 작업 범위와 겹치면 "서연님이 A2:A3 범위를 AI로 검토하는 중이에요. 겹치는 칸은 먼저 적용한 쪽이 반영돼요."를 띄운다. 둘 다 진행할 수 있다. 먼저 적용된 결과는 나중 사람에게 "원래 값이 바뀜"이 되어 건너뛰어진다. 그래서 충돌 처리는 첫 번째 규칙 한 곳에서 끝난다.
- 고르지 않은 안: 먼저 요청한 사람이 범위를 잠그는 방식. 탭끼리 주고받는 상태로는 같은 순간에 보낸 두 요청을 막을 수 없다. 탭이 비정상 종료되면 잠금이 최대 30초 남고, 누군가 시트 전체로 요청하면 모두가 막힌다. 이렇게 불완전한 잠금은 "막힌 줄 알았는데 겹쳤다"는 더 헷갈리는 상황을 만든다.

## 네트워크 기반 동기화로 확장한다면

바뀌지 않는 것부터 적는다. 문서 모델(`Y.Doc`의 셀 스키마), `@sheet/core` 전체, 실행 취소(내 origin만 추적), 화면은 그대로 둔다. Yjs update와 awareness는 전송 수단과 상관없는 바이너리다. 지금 BroadcastChannel로 보내는 메시지를 그대로 네트워크로 보내면 된다.

바뀌어야 하는 것은 여섯 가지다.

1. **전송 계층.** `apps/web/src/collab/broadcastProvider.ts`를 WebSocket 연결(y-websocket이나 Hocuspocus 서버)로 바꾼다. 지금 쓰는 메시지 세 종류(합류 인사인 state vector 교환, 문서 update, awareness update)는 Yjs sync 프로토콜의 step 1, step 2, update와 같다. 이미 있는 "다시 보이면 맞추기"(합류 인사 재전송)가 재연결 뒤 동기화를 맡을 자리다. 연결이 끊긴 동안의 편집은 IndexedDB에 남았다가, 다시 연결되면 CRDT가 병합한다.
2. **진실 공급원.** 지금은 브라우저마다 있는 IndexedDB가 저장소다. 앞으로는 서버가 문서 update를 DB(Postgres, S3 등)에 쌓고 주기적으로 스냅샷으로 합친다. IndexedDB는 오프라인 편집과 빠른 첫 화면을 위한 캐시로 남는다.
3. **문서 식별과 권한.** 지금은 origin 하나에 시트가 하나다(`sheet:v2:default`). URL에 문서 ID를 넣고(`/s/:id`) 서버가 방(room) 단위로 연결을 나눈다. 같은 origin의 탭끼리는 서로를 믿어도 되지만 네트워크에서는 그렇지 않다. 서버가 연결마다 인증하고, 읽기·쓰기 권한을 확인하고, update 크기를 제한해야 한다.
4. **참여자 정체성.** 지금은 탭 하나가 참여자 한 명이고, 이름은 탭마다 직접 정한다. 계정이 생기면 이름과 색은 계정에서 가져온다. 한 사람이 여러 탭이나 기기로 들어오면 사용자 단위로 묶어 보여 준다. 탭을 닫은 참여자 정리도 더 확실해진다. 지금은 `pagehide` 방송에 기대지만, 서버가 소켓 종료를 보고 그 참여자의 awareness를 지우면 된다.
5. **지연을 전제로 한 표시.** 네트워크 지연이 생기면 다른 사람의 커서와 편집이 늦게 보인다. AI 제안의 "원래 값이 바뀜" 판정도 내 탭에 도착한 값을 기준으로 하게 된다. 그래서 적용 직전에 서버 기준 값으로 한 번 더 확인하거나, 적용 뒤에 도착한 원격 변경은 CRDT 병합 결과를 그대로 보여 준다. 겹침 경고는 awareness로 지금처럼 동작한다.
6. **AI 호출 제한.** 지금은 공개 링크의 남용을 요청 크기 상한, 출력 길이 상한, 선불 한도로만 막는다. 계정이 생기면 사용자와 문서 단위의 호출 제한을 서버에 둔다.

```bash
node -v                 # v24.18.1 확인 — 다른 Node가 PATH 앞에 있으면 mise 버전이 가려진다
pnpm install
cp apps/web/.env.example apps/web/.env.local   # OPENAI_API_KEY 채우기 (AI 편집용)
pnpm dev                # http://localhost:3000
```

API 키는 서버에서만 읽는다(`apps/web/src/app/api/ai/route.ts`). 개발 서버는 **가짜 응답 모드**로 시작하고, 왼쪽 위 버튼으로 실제 AI와 바꿀 수 있다. 키가 없어도 가짜 응답으로 전체 흐름을 볼 수 있다. 배포본에서는 주소에 `?debug=1`을 붙였을 때만 이 버튼이 보인다.

배포본과 똑같이 보려면(실제 AI가 기본, 디버깅 버튼 숨김) 프로덕션 빌드로 실행한다. 이때는 `OPENAI_API_KEY`가 필요하다. 키가 없으면 주소에 `?debug=1`을 붙여 가짜 응답으로 바꾸면 된다.

```bash
pnpm build
pnpm start              # http://localhost:3000
```

공동 편집은 같은 브라우저에서 같은 주소를 탭 여러 개로 열어 확인한다. `localhost`와 `127.0.0.1`은 서로 다른 origin이라 둘 사이는 동기화되지 않는다.

## 검증

| 명령 | 내용 |
| --- | --- |
| `pnpm test` | `@sheet/core` 단위 테스트 (Vitest) |
| `pnpm typecheck` | 전 패키지 타입 검사 |
| `pnpm lint` | ESLint (Next 규칙) |
| `pnpm build` | 프로덕션 빌드 |
| `pnpm check` | 구조·문서 계약 검사 (`scripts/check-structure.sh`) |
| `pnpm e2e` | Playwright E2E. 실제 Chromium에서 편집, 여러 탭 공동 편집, AI 편집(가짜 응답) 시나리오를 돌린다. dev 서버(3100번 포트)를 스스로 띄운다. 처음 한 번은 `pnpm --filter @sheet/web exec playwright install chromium`이 필요하다 |

어떤 코드에 어떤 테스트가 필요한지는 `.codex/skills/test-policy/SKILL.md`에 정해 두었다.

최종 결과는 core 단위 테스트 60건, Playwright E2E 65건 통과다. E2E로 재현할 수 없는 것(실제 한글 입력기, 엑셀·구글 시트·구글 문서에서 붙여넣기, 오래 가려 둔 탭, 실제 AI 응답, Safari)은 사람이 실제 Safari와 Chrome에서 확인했다. 시나리오와 확인 기록은 `docs/manual-scenarios.md`에 있다.

## 개발 방식

구현은 AI Agent(Claude Code, Codex)가 맡고, 구조와 규약과 판단은 사람이 맡았다. Agent가 처음 읽는 문서는 `AGENTS.md`, 이 작업 체계의 설명은 `docs/AI_AGENT_HARNESS.md`, LLM 활용 기록은 `LLM_REPORT.md`다.
